measured. Real-data numbers come from `artifacts/metrics_ulb_creditcard.json`;

## Model details

- **Architecture:** `HistGradientBoostingClassifier` (scikit-learn), a single gradient-
  boosted-tree binary classifier, plus a reject-to-review knob layered on top of its
  probability output. This is the same reject-option idea as FlowSentry's two-stage
  classifier (from Sepehr Jafari's SECRYPT 2026 paper on hierarchical UDP/QUIC intrusion
  detection), translated from a multi-class top-1-confidence reject to a binary
  distance-from-decision-boundary reject: `confidence = max(p_fraud, 1 - p_fraud)`,
  range `[0.5, 1.0]`. Below a chosen threshold the system abstains and returns
  `"review"` instead of forcing a fraud/legit call.
- **Why HistGradientBoostingClassifier over xgboost:** it ships inside scikit-learn
  (already a dependency), so it installs cleanly everywhere - including CI - with no
  compiled-wheel risk, and it natively handles missing values in numeric features,
  which already matters for the real run (ULB's V1..V28 PCA columns) and will matter
  more for IEEE-CIS's sparse C/D/V columns. xgboost is a documented drop-in alternative.
- **Imbalance handling:** balanced **sample weights** (`n_samples / (n_classes *
  count_per_class)`, the same formula as scikit-learn's `class_weight="balanced"`),
  computed from the TRAIN split's own class counts and passed to `.fit(sample_weight=)`.
  This is a deliberate choice over resampling (SMOTE/undersampling): weighting never
  touches `X`, so it cannot suffer the classic "SMOTE fit before the split" leakage bug
  that the FINTECH_PLAN research specifically flags as the difference between a real
  0.86 PR-AUC and a fake 0.999. If a future run wants resampling, the rule is the same
  one that already applies here: fit it on the train split only.
- **Implementation:** `src/ledgersentry/model.py`, scikit-learn, seeded
  (`random_state=42`).

## Intended use

- Score a financial transaction for fraud risk and route it to one of three outcomes:
  auto-clear (`legit`), auto-flag (`fraud`), or `review` (send to a human / a heavier
  downstream check) when the model is not confident either way.
- Demonstrate and measure the coverage-vs-precision trade-off of a reject option
  applied to imbalanced binary fraud scoring - the same rigor FlowSentry sells for
  network intrusion detection, applied to money.

**Out of scope:** this is a research/portfolio baseline. It has been trained and
evaluated on one real public dataset (ULB, above), but it is not a production fraud
system and must not be pointed at live payments as-is. It is fraud-DETECTION
research/software; it never trades, moves money, or gives personalized financial
advice, and neither does any other part of this repo.

## Data

- **Real run:** ULB "Credit Card Fraud Detection" (`data/creditcard.csv`), 284,807
  transactions over 2 days, 492 fraud (0.173%), features `V1..V28` (PCA-anonymized
  by the dataset authors), `Amount`, `Time`. Obtained from the TensorFlow-hosted
  public mirror (`storage.googleapis.com/download.tensorflow.org/data/creditcard.csv`,
  the copy used by TensorFlow's official imbalanced-classification tutorial - no
  Kaggle login needed); file integrity verified after download (md5 matches the
  mirror's ETag, row count 284,807, fraud count 492). ULB has no card/customer id,
  so the grouped split degrades to a **pure temporal split** for this source: train
  = the first ~80% of transactions by time, test = the last ~20% (documented in
  `data.py`, not hidden).
- **Synthetic fixture:** synthetic, seeded, 8,000 rows, `fraud_rate=0.01` target (measured
  1.00% overall, 1.01% train / 0.95% test after the split - see below). Columns:
  `transaction_id, timestamp, entity_id, amount, category, is_fraud,
  f_entity_daily_tx_count`, plus engineered `hour_of_day, day_of_week`. Fraud rows get
  a shifted-but-overlapping distribution (heavier-tailed amounts, a higher chance of
  landing in a 00:00-05:00 window, skewed toward electronics/travel/online categories,
  a bumped same-day transaction count) - overlapping on purpose, so the classes are not
  trivially separable. See the docstring in `src/ledgersentry/data.py::make_synthetic`.
- **Split:** `temporal_grouped_split` - every row for a given `entity_id` (account)
  goes entirely to train or entirely to test (no account's history straddles the
  boundary), and accounts are assigned in ascending first-seen order, so the split is
  also approximately temporal: every train account is first seen no later than every
  test account. `entity_id` itself is excluded from the model's features - only ever
  used as the split's group key - so the model can't just memorize an account.
- **Other real sources supported (loaders CI-tested, full runs pending):** Sparkov
  (streaming/timestamp demo set), IEEE-CIS (headline benchmark), and the Amazon
  `fraud-dataset-benchmark` (comparability). All four loaders are exercised in CI
  against tiny true-schema fixtures (`tests/test_loaders.py`); drop the real file in
  `data/` and `python scripts/train.py` uses it automatically instead of the
  synthetic fallback - see README "Data" for exact filenames and links.

## Evaluation results - REAL DATA (ULB credit-card fraud)

**Measured 2026-07-15** by `python scripts/train.py` with `data/creditcard.csv`
present; source of truth `artifacts/metrics_ulb_creditcard.json`, tagged
`is_synthetic: false`.

**Split:** 227,846 train rows (417 fraud) / 56,961 test rows (75 fraud, 0.132%),
pure temporal for this source (see Data above): the model trains on the first ~40
hours of transactions and is evaluated on the final ~7.6 hours it has never seen.

**PR-AUC (average precision) on the real imbalanced holdout: 0.7278.**
Random/no-skill baseline on this test fold: **0.0013** - the model's PR-AUC is
roughly 550x the no-skill baseline. For context, published XGBoost-class results on
real card data sit around PR-AUC 0.86-0.88, but those are typically on random
(non-temporal) splits of different datasets; this 0.7278 is on a strictly temporal
holdout, which is the harder, more production-honest setting. The numbers are not
directly comparable and this page does not claim they are.

**Coverage vs precision on real data (the reject-to-review knob working):**

| Review threshold | Coverage | Sent to review | Flagged fraud | Precision on flagged |
|---|---|---|---|---|
| 0.50 | 100.00% | 0 | 216 | 29.17% |
| 0.60 | 99.76% | 139 | 156 | 38.46% |
| 0.70 | 99.45% | 312 | 129 | 44.19% |
| 0.80 | 98.98% | 583 | 105 | 53.33% |
| 0.90 | 97.22% | 1,582 | 73 | 73.97% |
| 0.95 | 92.91% | 4,039 | 59 | 89.83% |
| 0.99 | 0.03% | 56,943 | 0 | undefined (nothing flagged) |
| 1.00 | 0.00% | 56,961 | 0 | undefined (nothing flagged) |

Reading it: on real data the knob genuinely earns its keep. Fully automated
(threshold 0.50), the model flags 216 transactions and 29% of them are truly fraud.
Send the most uncertain 7.1% of traffic to human review (threshold 0.95) and the
automated fraud flags become 89.8% precise - a 3x precision lift for reviewing
4,039 of 56,961 transactions. The cliff at 0.99 is honest and expected: the model's
uncalibrated confidence almost never exceeds 0.99 on this data, so that threshold
sends essentially everything to review (see Limitations, "uncalibrated
confidence"). Between 0.50 and 0.95 the curve is smooth and monotonic - unlike the
synthetic fixture's nearly flat curve below, this is what the knob looks like with
real volume behind it.

## Evaluation results - SYNTHETIC FIXTURE (offline CI baseline)

These are the deterministic fixture's numbers (`is_synthetic: true`), kept for what
they are: the offline CI baseline that proves the pipeline works with zero downloads.
They are NOT real-data results - those are the section above.

**Split:** 6,419 train rows / 1,581 test rows (grouped + approximately temporal, zero
entity overlap). Test fraud rate 0.95% (15 fraud rows out of 1,581).

**PR-AUC (average precision) on the imbalanced holdout: 0.7884.**
Random/no-skill baseline on this test fold (a scorer with no signal has PR-AUC equal
to the positive rate): **0.0095**. The model's PR-AUC is ~83x the no-skill baseline -
real, non-trivial signal, and honestly short of 1.0, consistent with fraud rows being
built to overlap the legit distribution rather than being cleanly separable.

**Coverage vs precision (the reject-to-review knob working).** Coverage = fraction of
the 1,581 test rows the model decides on its own (not sent to review). Precision =
of the rows it flags as fraud within that covered subset, what fraction are truly
fraud.

| Review threshold | Coverage | Sent to review | Flagged fraud | Precision on flagged |
|---|---|---|---|---|
| 0.50 | 100.00% | 0 | 13 | 76.92% |
| 0.60 | 99.94% | 1 | 13 | 76.92% |
| 0.70 | 99.87% | 2 | 12 | 83.33% |
| 0.80 | 99.81% | 3 | 11 | 81.82% |
| 0.90 | 99.81% | 3 | 11 | 81.82% |
| 0.95 | 99.68% | 5 | 10 | 90.00% |
| 0.99 | 99.30% | 11 | 9 | 88.89% |
| 1.00 | 0.00% | 1,581 | 0 | undefined (nothing flagged) |

Source: `artifacts/metrics_synthetic.json`. Reading it: at the loosest setting the model
auto-decides every transaction and is right on 76.9% of the ones it flags as fraud;
tightening the knob trades a handful of auto-decisions for review (at most 11 of 1,581
at threshold 0.99) and lifts flagged-fraud precision to 88-90%. The curve is not
monotonic between 0.70 and 0.90 (0.8333 dips to 0.8182) because at n=11-13 flagged
transactions, one label flip moves precision by ~9 percentage points - the honest
noise floor of a 1,581-row test fold, not a modeling claim. The real-data section
above shows what the same knob looks like with actual volume behind it.

## Why these numbers, not higher ones (and why that's reported anyway)

A PR-AUC near 1.0 on a fraud task is usually a leakage smell, not a win - see the
FINTECH_PLAN research on SMOTE-before-split producing a fake "AUC 1.000." The real
0.7278 and the synthetic 0.7884 both sit in a believable range precisely because the
split was built to block leakage on purpose (and, for the fixture, because the
generator overlaps its classes on purpose). The honest published range for a mature
model on real imbalanced card data is roughly PR-AUC 0.86-0.88 (XGBoost, per the
cited MDPI/arXiv sources), typically on random splits; this repo's real number is on
a stricter temporal holdout of a different dataset and is not claimed to be
comparable. A defensible measured 0.73 under honest evaluation beats a fake 0.99,
and that trade is the whole point of this project.

## Limitations (honest)

1. **One real dataset so far.** The real-data results above are ULB only. Sparkov,
   IEEE-CIS, and Amazon FDB have schema-tested loaders (CI-exercised on tiny
   fixtures) but no full-scale run yet - their downloads are Kaggle/auth-gated.
2. **ULB's split is temporal, not grouped.** ULB publishes no card/customer id, so
   the entity-grouped guarantee cannot apply there; the split is purely temporal for
   that source. The grouped+temporal guarantee is CI-tested and will bind on
   Sparkov/IEEE-CIS/FDB, which do have entity keys.
3. **Small test fold on the synthetic fixture.** 1,581 rows / 15 fraud means the
   fixture's coverage-precision curve has real sampling noise at the tightest
   thresholds. The real ULB fold is larger (56,961 rows / 75 fraud) but 75 positives
   still leaves visible noise in per-threshold precision; do not over-read small
   differences between adjacent rows.
4. **Uncalibrated confidence.** `max(p_fraud, 1-p_fraud)` is a HistGradientBoosting
   probability estimate, not a calibrated probability. On real ULB data the
   confidence almost never exceeds 0.99 (the measured coverage cliff in the table
   above), so thresholds are meaningful only against the measured curve for the
   dataset in front of you. Train-set-only calibration (CalibratedClassifierCV) is
   the documented next step.
5. **No adversarial or drift evaluation.** Out of scope for this baseline; a
   documented next step, mirroring FlowSentry's Week-3 threat-model work.
6. **Latency is measured on the synthetic fixture only.** The F2 streaming replay
   (README "Live serving") measured per-row latency on the synthetic test split;
   the real-data replay at volume is still to come.
7. **Feature set is what the source provides, nothing engineered beyond time.**
   For ULB that is the 28 PCA components + `Amount` + engineered `hour_of_day` /
   `day_of_week`; for the fixture, `amount`, time features, `category`, and one
   velocity feature. No entity-level aggregate features are built yet (ULB has no
   entity to aggregate on; Sparkov/IEEE-CIS runs can add them).
