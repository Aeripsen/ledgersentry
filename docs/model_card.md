# Model card: LedgerSentry FraudDetector

Version 0.1.0 (F1 milestone: synthetic-fixture baseline). Every number on this page is
measured, comes from `artifacts/metrics.json`, and is regenerated by every run of
`python scripts/train.py`.

> **Data note, read this first.** All numbers below are measured on a **deterministic
> synthetic transaction set** (`src/ledgersentry/data.py::make_synthetic`), not on real
> financial data. This is a fixture, not a benchmark result - it exists so the pipeline,
> tests, and CI are green with no network access and no Kaggle-gated download. Every
> metrics artifact this repo produces carries `is_synthetic: true` for exactly this
> reason. The real-data run (Sparkov / IEEE-CIS / ULB / Amazon FDB) is a documented,
> not-yet-executed next step - see README "Data" and HANDOFF.md.

## Model details

- **Architecture:** `HistGradientBoostingClassifier` (scikit-learn), a single gradient-
  boosted-tree binary classifier, plus a reject-to-review knob layered on top of its
  probability output. This is the same reject-option idea as FlowSentry's two-stage
  classifier (from Sepehr Jafari's SECRYPT 2026 paper on hierarchical UDP/QUIC intrusion
  detection), translated from a multi-class top-1-confidence reject to a binary
  distance-from-decision-boundary reject: `confidence = max(p_fraud, 1 - p_fraud)`,
  range `[0.5, 1.0]`. Below a chosen threshold the system abstains and returns
  `"review"` instead of forcing a fraud/legit call.
- **Why HistGradientBoostingClassifier over xgboost:** it ships inside scikit-learn
  (already a dependency), so it installs cleanly everywhere - including CI - with no
  compiled-wheel risk, and it natively handles missing values in numeric features,
  which will matter once a real dataset with sparse anonymized columns (ULB's V1..V28,
  IEEE-CIS's C/D/V columns) is dropped in. xgboost is a documented drop-in alternative.
- **Imbalance handling:** balanced **sample weights** (`n_samples / (n_classes *
  count_per_class)`, the same formula as scikit-learn's `class_weight="balanced"`),
  computed from the TRAIN split's own class counts and passed to `.fit(sample_weight=)`.
  This is a deliberate choice over resampling (SMOTE/undersampling): weighting never
  touches `X`, so it cannot suffer the classic "SMOTE fit before the split" leakage bug
  that the FINTECH_PLAN research specifically flags as the difference between a real
  0.86 PR-AUC and a fake 0.999. If a future run wants resampling, the rule is the same
  one that already applies here: fit it on the train split only.
- **Implementation:** `src/ledgersentry/model.py`, scikit-learn, seeded
  (`random_state=42`).

## Intended use

- Score a financial transaction for fraud risk and route it to one of three outcomes:
  auto-clear (`legit`), auto-flag (`fraud`), or `review` (send to a human / a heavier
  downstream check) when the model is not confident either way.
- Demonstrate and measure the coverage-vs-precision trade-off of a reject option
  applied to imbalanced binary fraud scoring - the same rigor FlowSentry sells for
  network intrusion detection, applied to money.

**Out of scope:** this is a baseline trained on a synthetic fixture. It is not trained
on real transaction data and must not be pointed at real payments as-is. It is
fraud-DETECTION research/software; it never trades, moves money, or gives personalized
financial advice, and neither does any other part of this repo.

## Data

- **This run:** synthetic, seeded, 8,000 rows, `fraud_rate=0.01` target (measured
  1.00% overall, 1.01% train / 0.95% test after the split - see below). Columns:
  `transaction_id, timestamp, entity_id, amount, category, is_fraud,
  f_entity_daily_tx_count`, plus engineered `hour_of_day, day_of_week`. Fraud rows get
  a shifted-but-overlapping distribution (heavier-tailed amounts, a higher chance of
  landing in a 00:00-05:00 window, skewed toward electronics/travel/online categories,
  a bumped same-day transaction count) - overlapping on purpose, so the classes are not
  trivially separable. See the docstring in `src/ledgersentry/data.py::make_synthetic`.
- **Split:** `temporal_grouped_split` - every row for a given `entity_id` (account)
  goes entirely to train or entirely to test (no account's history straddles the
  boundary), and accounts are assigned in ascending first-seen order, so the split is
  also approximately temporal: every train account is first seen no later than every
  test account. `entity_id` itself is excluded from the model's features - only ever
  used as the split's group key - so the model can't just memorize an account.
- **Real sources supported (not run in this milestone):** Sparkov (streaming/timestamp
  demo set), IEEE-CIS (headline benchmark), the Amazon `fraud-dataset-benchmark`
  (comparability), and the ULB `creditcard.csv` (classic leakage-safe baseline). Drop
  the file in `data/` and `python scripts/train.py` uses it automatically instead of
  the synthetic fallback - see README "Data" for exact filenames and links.

## Evaluation results (measured, synthetic fixture)

**Split:** 6,419 train rows / 1,581 test rows (grouped + approximately temporal, zero
entity overlap). Test fraud rate 0.95% (15 fraud rows out of 1,581).

**PR-AUC (average precision) on the imbalanced holdout: 0.7884.**
Random/no-skill baseline on this test fold (a scorer with no signal has PR-AUC equal
to the positive rate): **0.0095**. The model's PR-AUC is ~83x the no-skill baseline -
real, non-trivial signal, and honestly short of 1.0, consistent with fraud rows being
built to overlap the legit distribution rather than being cleanly separable.

**Coverage vs precision (the reject-to-review knob working).** Coverage = fraction of
the 1,581 test rows the model decides on its own (not sent to review). Precision =
of the rows it flags as fraud within that covered subset, what fraction are truly
fraud.

| Review threshold | Coverage | Sent to review | Flagged fraud | Precision on flagged |
|---|---|---|---|---|
| 0.50 | 100.00% | 0 | 13 | 76.92% |
| 0.60 | 99.94% | 1 | 13 | 76.92% |
| 0.70 | 99.87% | 2 | 12 | 83.33% |
| 0.80 | 99.81% | 3 | 11 | 81.82% |
| 0.90 | 99.81% | 3 | 11 | 81.82% |
| 0.95 | 99.68% | 5 | 10 | 90.00% |
| 0.99 | 99.30% | 11 | 9 | 88.89% |
| 1.00 | 0.00% | 1,581 | 0 | undefined (nothing flagged) |

Source: `artifacts/metrics.json`. Reading it: at the loosest setting the model
auto-decides every transaction and is right on 76.9% of the ones it flags as fraud;
tightening the knob trades a handful of auto-decisions for review (at most 11 of 1,581
at threshold 0.99) and lifts flagged-fraud precision to 88-90%. The curve is not
monotonic between 0.70 and 0.90 (0.8333 dips to 0.8182) because at n=11-13 flagged
transactions, one label flip moves precision by ~9 percentage points - the honest
noise floor of a 1,581-row test fold, not a modeling claim. A real-data run will have
enough volume for a smoother curve.

## Why these numbers, not higher ones (and why that's reported anyway)

A PR-AUC near 1.0 on a fraud task is usually a leakage smell, not a win - see the
FINTECH_PLAN research on SMOTE-before-split producing a fake "AUC 1.000." This
baseline's 0.7884 sits in a believable range precisely because the synthetic generator
was built to overlap classes on purpose and the split was built to block leakage on
purpose. The honest published range for a mature model on real imbalanced card data is
roughly PR-AUC 0.86-0.88 (XGBoost, per the cited MDPI/arXiv sources in FINTECH_PLAN.md)
- this baseline is not that number, is not claimed to be that number, and is not
directly comparable to it since it is a different (synthetic) dataset entirely.

## Limitations (honest)

1. **Synthetic data only.** Nothing on this page says anything about performance on
   real transactions. The real-data run (Sparkov/IEEE-CIS/ULB/Amazon FDB) is
   documented and not yet executed - see HANDOFF.md.
2. **Small test fold.** 1,581 rows / 15 fraud means the coverage-precision curve has
   real sampling noise at the tightest thresholds (n as low as 9-13 flagged
   transactions); do not over-read small differences between adjacent rows.
3. **No cross-dataset generalization test.** Only one synthetic configuration
   (`seed=42`) is reported here, though `tests/test_data.py` checks a second seed
   produces different data (determinism, not generalization).
4. **Uncalibrated confidence.** `max(p_fraud, 1-p_fraud)` is a HistGradientBoosting
   probability estimate, not a calibrated probability; threshold values are meaningful
   only against the measured curve for this dataset, the same caveat FlowSentry's
   model card makes for its own confidence scores.
5. **No adversarial or drift evaluation.** Out of scope for this baseline; a
   documented next step (F2+), mirroring FlowSentry's Week-3 threat-model work.
6. **Latency is unmeasured.** No serving layer exists yet in this milestone (F2 adds
   the `/predict` endpoint + dashboard, mirroring FlowSentry's Week 2).
7. **Feature set is intentionally minimal.** `amount`, `hour_of_day`, `day_of_week`,
   `category`, and one velocity feature (`f_entity_daily_tx_count`). Real sources carry
   many more numeric columns (ULB's 28 PCA components, IEEE-CIS's C-columns), which
   `data.py` already passes through as `f_*` features and the preprocessor already
   picks up automatically - untested until a real file is dropped in.
