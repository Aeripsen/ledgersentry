LedgerSentry, live demo

Drag the review knob. See what a fraud desk gets.

A fraud model that does not have to guess. When it is unsure it sends the transaction to a human instead of blocking or approving it. The knob below is counted in your browser from 56,961 real card transactions the model never saw in training (the last 7.65 hours of the public ULB dataset, 75 of them fraud). The headline tiles read the committed business-case file. Nothing is simulated, and no model runs here: the scores come from the model the repo's committed code retrains deterministically.

Three policies on the same held-out transactions: A decides everything with one cut at 0.5; B raises that cut to 0.95 and still decides everything; C is B plus a review band for the uncertain middle. The false-alert drop is all B's doing (C has the same alerts); what the review band adds is the frauds it keeps from being cleared unseen. Whether a reviewer then catches them is not measured. Figures from artifacts/business_case_ulb_creditcard.json; brackets are 95% bootstrap intervals, and with 75 frauds in one fold they are a floor on the uncertainty.

The knob

0.500 = decide everything (the baseline). Higher = more goes to a human. Tick marks are the committed table's rows (0.5 to 1.0); CI checks that the page's counts equal the table at every one. Above 0.95 almost everything goes to review.

These cuts are on the model's raw score, which ranks transactions but is not a probability: a cut at 0.9 does not mean "90% likely fraud". The repo's own decoupled-cut analysis (ADR 008) uses calibrated scores for that reason; this view does not. The approve cut stops below the block cut's lowest setting, so no transaction can be in both lanes. With the approve cut at 1 minus the block cut, the counts equal the single knob.

How you can check this

  • The scores are raw fraud scores on a strictly temporal holdout: trained on the first ~40 hours, tested on the last 7.65 (the last training transaction is one second before the first test one; no second is shared). No model file is committed. They come from the model the repo's committed code retrains deterministically (make reproduce), exported by make demo-data, and are downloadable above. The page does the counting live; it does not run the model in your browser.
  • This page deploys only after the repo's whole ci workflow passes on the same commit. That run fetches the public ULB file (sha256-checked), retrains, and requires these rows back byte for byte (scripts/demo_data.py --verify); rebuilds the committed knob table, the PR-AUC of 0.7278 and the business case's policies, sweep, intervals and sentences from them (tests/test_demo_data.py); and loads this page in headless Chromium, checking its counts against the committed table at every tick mark (0.5 to 1.0) and its headline against the business case (scripts/check_site.py).
  • 75 frauds is a small number. One fraud is 1.3 points of recall, which is why the headline carries intervals. They are a floor on the uncertainty: the bootstrap treats rows as independent and fraud comes in bursts.
  • There is no "type in a transaction" box on purpose. ULB's 28 features are anonymized PCA components, so there is nothing meaningful for a person to type.
  • No dollar savings are claimed anywhere. What a review or a missed fraud costs is a business number this repo cannot know.
